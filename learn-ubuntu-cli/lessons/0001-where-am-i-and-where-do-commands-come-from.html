Where am I, and where do commands come from?

Lesson 1 · Ubuntu on WSL · about 15 minutes

Almost every early WSL frustration is one of two questions in disguise: which filesystem am I standing in? and where is Bash looking for this command? Answer both and command not found stops being a wall and becomes a diagnosis.

You already know PowerShell. That is an asset and a trap. The asset: you know what a shell is — a program that reads a line, resolves a name, runs it. The trap: in PowerShell, ls, dir and Get-ChildItem are all the same thing, because PowerShell ships aliases for them. In Bash they are not the same thing at all, and two of them don't exist. Your muscle memory will keep proposing commands that Ubuntu has never heard of, and the error message won't explain why.

This lesson gives you the two mental models that make the error message explain itself. It is the foundation for the next three things on your mission — VS Code, Claude Code, and Docker — because each of those is installed somewhere, on some filesystem, and found (or not found) through the same lookup rule.

1 · Two filesystems, one prompt

WSL gives you a real Linux filesystem. Its root is /, and your home directory is /home/<your-name> — nothing to do with C:\Users\. Your Windows drives are then mounted into that Linux tree: Microsoft documents that Windows drives appear under /mnt/, so C:\Users\you\Project is reachable from Bash as /mnt/c/Users/you/Project. [MS: Working across file systems] 

$ pwd
/home/josh
$ ls /mnt/c
'Program Files'   Users   Windows   ...

It goes the other way too: type \\wsl$ into Windows File Explorer and you'll see the Linux side from Windows.

So there is one prompt but two worlds, joined at /mnt/. Which world a file lives in is not cosmetic — it changes behaviour:

ConcernLinux side (/home/you)Windows side (/mnt/c/...)
Case Notes.txt and notes.txt are two files Windows treats them as one
Docker bind mounts Fast; containers receive file-change events Slow; file-change events are lost
Permissions Real Linux ownership and modes Synthesised — often everything looks executable
The rule that will save you a week

Keep the projects you'll build in inside the Linux filesystem — /home/you/code/..., not /mnt/c/Users/.... Docker's own documentation is blunt about it: mounting from /mnt/c goes through a Plan 9 file share, so you lose the performance and the inotify events that hot-reload and file-watchers depend on. [Docker: WSL 2 best practices] VS Code's WSL Remote mode is built for exactly this: the editor UI runs on Windows, the files and tools stay on Linux.

2 · How Bash finds a command

When you type docker, Bash does not search your computer. It walks a list of directories held in an environment variable called PATH, in order, and runs the first executable file with that name it finds. If it reaches the end of the list, you get command not found. [GNU Bash manual: Command Search and Execution]

PATH is a single string of directories separated by colons. Split it onto separate lines to read it: 

$ echo $PATH | tr ':' '\n'
/usr/local/sbin
/usr/local/bin
/usr/sbin
/usr/bin
/home/josh/.local/bin
/mnt/c/Windows/system32
/mnt/c/Users/josh/AppData/Local/Programs/Microsoft VS Code/bin

Those last highlighted entries are the second surprise: WSL appends your Windows PATH onto your Linux one. That is why notepad.exe and code work from Bash — you are genuinely launching Windows programs from a Linux shell, and Microsoft documents them as first-class: you can pipe to and from them. [MS: Working across file systems]

Three commands let you interrogate this, and they are not interchangeable:

CommandAnswers
type lsWhat kind of thing is this name? File, alias, shell builtin, or function.
type -a lsEvery match, in the order Bash would consider them. Shows shadowing.
which lsOnly the file on PATH. Blind to aliases, builtins, and functions.

Prefer type. which will happily tell you /usr/bin/ls while the thing you actually ran was an alias with different flags — which is precisely the confusion you don't need while learning.

3 · Reading command not found

It has exactly three causes, and type plus one guess tells you which:

  1. It isn't installed. The usual case for docker, claude, gh, jq. Fix: install it — usually sudo apt install <name>, sometimes a vendor installer.
  2. It's installed, but not on PATH. Very common right after an install script drops a binary in ~/.local/bin. Fix: open a new shell, or add the directory to PATH.
  3. It doesn't exist in this world. Get-ChildItem, Select-String, curl -UseBasicParsing — PowerShell ideas with different Bash spellings. Fix: translate it. That's what the PowerShell → Bash reference sheet is for.

Cause 2 is the one that feels like a bug and isn't. An installer prints "success", you type the command, and Bash says it doesn't exist — because your current shell read PATH when it started and hasn't re-read it. Claude Code's installer, for instance, places its launcher at ~/.local/bin/claude. [Claude Code: Advanced setup] If claude isn't found straight after installing, the file almost certainly exists — check with ls ~/.local/bin before you reinstall anything.
